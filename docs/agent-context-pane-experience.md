# Agent + Context Pane Experience

## 一句话

Lets 里的 agent 不应该像第 4 个一直发言的人，而应该像一个强力思考辅助：人类在聊天流里自然讨论，agent 在合适的时候介入，同时持续维护右侧活的 Context pane。

好的体验是：聊天不被打断，但讨论不会蒸发。

## 场景

一个 topic 里有 3 个人和 1 个 agent。

3 个人主要在中间聊天流里讨论：

- 提想法
- 争论方案
- 补充约束
- 做决定
- 临时跑题
- 回到主线

agent 默认不抢话。它旁听、理解、判断什么时候需要出手，并把讨论沉淀到右侧 Context pane。

## 三层产品结构

### 1. 聊天流：讨论过程

聊天流是人类自然交流的地方。这里应该保留轻松、连续、低摩擦的感觉。

agent 可以进入聊天流，但必须克制。它的发言应该短、准、有推进价值。

### 2. Context pane：活的工作记忆

Context pane 是 agent 持续维护的结构化讨论状态。它不是普通摘要，也不是一次性会议纪要，而是会随着聊天不断变化的共享白板。

它应该承载：

- 当前意图
- 已形成的共识
- 候选方案
- 约束条件
- 待回答问题
- 盲点
- 反方观点
- 延展想法
- 图和资料

### 3. Spec / 输出：阶段性产物

当讨论成熟后，用户可以从 Context pane 生成或分享 Spec。Spec 是阶段性产物，Context pane 是持续演化的中间状态。

## Agent 的两个循环

### 静默循环：维护 Context pane

agent 大部分时间应该在静默循环里工作。

它观察聊天，但不一定发言。它应该自动把讨论里的重要结构沉淀到右侧：

- 把“就这么定了”收进共识
- 把 A/B/C 路线整理成候选方案
- 把“不能上传文件正文”识别为约束
- 把没人回答的问题放进待回答
- 把潜在风险放进盲点
- 把明显反对理由放进反方观点
- 把可探索的相邻方向放进延展想法

用户的感受应该是：

> 我们只是在聊天，但右边的思考板自己变清楚了。

### 介入循环：推动讨论

agent 只有在有推进价值时才进入聊天流。

适合介入的时机：

- 发现隐藏分歧：两个人用同一个词指不同东西
- 发现重大遗漏：权限、成本、风险、边界没人提
- 发现讨论可以收束：已经接近一个决定
- 发现问题悬而未决：待回答的问题阻塞下一步
- 发现讨论跑偏：当前消息和 topic 目标偏离太远
- 发现需要拆 topic：出现独立子问题
- 被人明确 @

不适合介入的时机：

- 只是复述大家刚说过的话
- 每几条消息就发一段总结
- 为了展示聪明而扩展话题
- 把人类还在探索的问题过早定论
- 用长篇建议打断聊天节奏

## 一个理想片段

人类聊天：

> Jacky：我想做一个自然语言文件检索工具。  
> Neo：我担心权限和索引成本。  
> CC：要不要先只做本地文件夹版本？  
> Jacky：但我希望能问“上周那个合同在哪”。  

此时 agent 不一定发消息。右侧 Context pane 更新：

- 正在讨论：自然语言文件检索工具
- 候选方案：
  - 本地文件夹索引 MVP
  - 云端同步索引
  - 只接现有文档源
- 约束：
  - 权限边界必须清晰
  - 索引成本不能太高
- 待回答：
  - 是否需要跨设备？
  - 搜索对象包括正文还是只包括文件名？
- 盲点：
  - 文件权限变更后，旧索引如何失效？

如果讨论继续模糊，agent 再短暂介入：

> 我注意到这里有一个隐含分歧：Jacky 想要“按语义找内容”，CC 提的是“先做本地文件夹索引”。要不要先把 MVP 定成“本地文件夹 + 文件名/摘要检索”，正文索引放到下一步？

这类介入是好的，因为它帮助讨论收束，而不是抢话。

## Context pane 条目的理想属性

每个条目都应该让用户知道它从哪里来、是否可靠、现在是什么状态。

### 来源

每个条目应该能跳回来源消息。

示例：

> 约束：不能上传文件正文  
> 来自 Jacky 10:17，agent 总结

如果来源是多条消息，可以显示：

> 来自 Jacky 10:17、Neo 10:21

### 状态

条目不应该只有“存在”这一种状态。至少应该有：

- agent 推断
- 人已确认
- 人已编辑
- 已解决
- 已过期

示例：

> 可能的约束：不能上传文件正文  
> agent 推断，未确认

用户确认后：

> 约束：不能上传文件正文  
> Jacky 已确认

### 归属

多人讨论中，agent 不应该抹平人的贡献。

不好的表达：

> 我们决定先做本地 MVP。

更好的表达：

> 当前倾向：先做本地 MVP  
> Jacky 提出，Neo 补充权限约束，CC 尚未表态

### 可操作

Context pane 不是只读摘要。用户应该能轻量维护它：

- 确认
- 编辑
- 删除
- 标记已解决
- 标记过期
- 转成共识
- 转成候选方案
- 拆成新 topic

## Agent 发言风格

agent 在聊天流里的发言应该符合几个原则：

### 短

默认 1-3 句话。除非用户明确要求展开。

### 有判断

不要只列选项。要能说：

> 我倾向先做本地 MVP，因为权限边界最容易控制。

### 有上下文意识

agent 应该引用当前讨论，而不是泛泛建议。

### 有边界

如果只是更新了 Context pane，可以只轻轻提示：

> 我把刚才的讨论整理到右侧了：新增 2 个候选方案和 1 个权限风险。

很多时候甚至不需要提示。

## 节奏控制

agent 不应该每条消息都更新可见 UI，也不应该每次更新都发言。

建议节奏：

- 每 5-10 条消息做一次批量整理
- 用户停顿几秒后整理
- 出现明确结构信号时立即整理，例如“就这么定了”“问题是”“方案 A”
- 被 @ 时立即响应
- 发现重大风险或隐含分歧时介入聊天流

右侧新增内容可以短暂高亮，显示“刚刚更新 3 项”。不要弹窗，不要打断输入。

## 好体验的判断标准

一个好的 3 人 + 1 agent topic，应该让用户产生这些感受：

- 我没有被 AI 打断
- 但 AI 一直在帮我思考
- 我能快速知道当前讨论到哪了
- 后加入的人能快速追上
- 重要决定不会埋在聊天历史里
- 分歧和风险不会被忽略
- 输出 Spec 时不需要重新整理一遍

反过来，坏体验是：

- agent 一直刷长消息
- 右侧只是机械摘要
- 条目没有来源，用户不信
- agent 把未确认的推断写得像事实
- Context pane 越堆越多，没人维护
- 人类贡献被 agent 的总结抹平

## V1 落地建议

第一版不要追求复杂自动化，先把信任链路做出来。

优先级：

1. Context pane 顶部明确说明：由 agent 自动维护。
2. 每个条目显示来源，并能跳回原消息。
3. 每个条目标注是 agent 总结还是人手动加入。
4. agent 更新 Context pane 时，新条目短暂高亮。
5. 待回答问题支持“答 / 略 / 已解决”。
6. agent 插话要节流，只在关键情况进入聊天流。
7. Spec 从 Context pane 生成，而不是从原始聊天硬拼。

## 产品定位

Lets 不应该只是“群聊 + AI 回复”。

更准确的定位是：

> 一个多人讨论空间，agent 把聊天持续沉淀成可操作的共享上下文。

聊天流负责自然交流。Context pane 负责结构化记忆。agent 负责把两者连接起来。
